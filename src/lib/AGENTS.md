## Jackboy feature rules (src/lib and their routes)
- Technology Discovery lives in `src/lib/discovery.ts` (source registry, dedupe, ranking, local state) and `src/routes/discovery.tsx`; it is opt-in and uses demo data until a backend can fetch public APIs/RSS on a schedule. Facts and AI hypotheses must stay visually separated.
- JAX is the commercialization/distribution hub. Release manifests (contract `jax.release-manifest/*`) live in `src/lib/jax.ts` + `src/routes/jax.tsx`; manifests stay `simulated: true` and `actualRevenue: null` until OMNI/JAX/payments are verified. Data-product revenue/distribution is gated by `dataProductCleared`; prohibited items (code, user data, credentials, PII, telemetry, third-party content, Vault) are never included.
- Discovery runs two tracks (`meta(f).track`): commercial (rankScore) and frontier/underdog (`frontierScore`, which must never take funding/publicity/citations/team size/sales as inputs). `mixTracks` reserves the owner-set frontier share (min 20%); `gemReasons` gives explainable overlooked-gem flags.
- Agent Hub (`src/lib/agent-hub.ts` rules, `agent-hub.functions.ts`, `/agents`, ingest at `/api/public/agent-ingest`): projects are opt-in; ingest uses project-scoped write-only tokens stored as SHA-256 hashes in `agent_project_tokens` (no client grants); DemonTech is limited to the defensive allowlist and owner-enabled per project; proposals are decided only via owner-only `decide_proposal` RPC and `tests_passed` stays false until a real sandbox runner exists.
- Automation policy (`src/lib/automation-policy.ts` rules, `automation.functions.ts`, `/automation`): single-row `automation_policy` changed only via owner-only `set_automation_policy` RPC (logged); `routeApproval` sends high-risk areas and production deploys to the owner at every tier; `guardian_verified` and `OMNI_VERIFIED` stay false until a real authenticated check exists; retrieval uses owner-checked `playbooks` only, never private code or self-modification.
- Agent Fleet (`src/lib/guardian.ts`, `fleet.functions.ts`, `/fleet`): `agents` rows are per project; clients can update only name/specialty/autonomy/paused (column grants), so `installed_verified`/health are server-set. `guardianCheck` is deny-by-default (pause → verified install → project isolation → required integration → owner-only capabilities → autonomy tier); server `INTEGRATIONS` stay false until real checks exist. Emergency pause reuses `automation_policy.paused`.
- Agent Passport (`passport.functions.ts`, `/passport/$agentId`): Guardian denies any agent without `passport_approved`, set only by owner-only `approve_passport` RPC; a DB trigger voids approval when model/adapter/category/project/autonomy change. JAX enrollment is per agent via owner-only `set_jax_enrollment` (consent purpose required, Vault rejected). `omni_jobs` are inserted as `queued` with no `sent_at`; only a verified OMNI dispatcher (server-side, not yet built) may mark them sent. Ingest accepts optional `agent_id`, checked against project, category, passport and pause.
- RA'SUL integration (`src/lib/razul.ts` rules, `razul.functions.ts`, `/razul`): server-only via `RAZUL_API_URL`/`RAZUL_API_KEY` secrets; findings without a source URL, timestamp and evidence class are rejected (DB check too); routed OMNI jobs stay queued-unsent; feedback `sent_at` set only after a successful live POST.
- Update writer (`update-writer.ts` rules, `.server.ts`, `github.server.ts`, `feeds.ts`, `/projects` `/updates` `/feeds`, hourly cron + per-project frequency, webhook `/api/public/feeds/$sourceId` with hashed per-source token): owner-only RLS; DB lease + batch bound + monthly AI/run caps auto-pause; GitHub writes only to private repos via branch+PR, merge gated by `canMerge` (checks), revert restores stored previous contents; email alerts stay `not_configured` until a sender domain exists.
- Update server: pure rules in `update-server.ts` (tested), admin runtime in `update-server.server.ts`, owner fns in `releases.functions.ts`; public endpoints under `/api/public/updates/*` return only signed release/flag data keyed by a non-secret project `client_key`; signing key is derived from the `JACKBOY_SIGNING_SECRET` secret, so rotating it changes the public key.
- Autopilot (`autopilot.ts` tested rules, `autopilot.server.ts`, `autopilot.functions.ts`, `/autopilot`, hourly tick inside `/api/public/jobs/releases`): ships only when master AND project switches are on, checks are `success`, and no sensitive paths are touched (`canAutoShip`); otherwise fixes wait in the Update Queue. Auto-connect commits the shared `update-client-snippet.ts` via PR to private repos only. Site scans are static HTML (no JS). Chat (`chat.server.ts`, `/api/chat`, `/chat`) verifies owner bearer in the handler, uses tools over real data only, no chat history persistence.
- Demo findings (`detectDemo` in `autopilot.ts`) are review leads, not proof; "Remove Demo" always calls `writeFix(..., { forceApproval: true })` so it never auto-ships, and per-finding decisions live in `finding_decisions` keyed by `findingKey`.
- Chat voice is browser-only (`src/components/ChatVoice.tsx`: SpeechRecognition fills the editable input, speechSynthesis reads replies); no audio is recorded or stored, and controls hide when unsupported.
- Repo coding goes only through `repo-workspace.server.ts` (guards in `repo-workspace.ts`): private repos with push access, writes only on `jackboy/*` branches, protected paths refused, draft PRs only, never merge; chat must call `capabilities` before claiming build/test ability and never paste code instead of writing it.
- Code Foundry (`foundry.ts` tested state machine, `foundry.server.ts`, `foundry.functions.ts`, `/foundry`, tick inside `/api/public/jobs/releases`): tasks move only via `assertTransition`; every change appends to `foundry_events`, which a trigger makes immutable (no update/delete). Approval sets exactly one `approved_action` (draft PR or read checks) that runs once with an idempotency key and bounded attempts; connector failures → `blocked`, never fake success. Recurring inspections are off by default, rotate one project per run, dedupe by `(project_id, dedupe_key)` and respect a daily quota. Tokens stay in backend secrets, never in tables.
- Foundry pipeline: after a completed task `advance` reports the next awaiting task or runs one budgeted inspection of the next project; the hourly tick retries due transient-blocked tasks with exponential backoff (`backoffMs`) and honors global pause, daily run budget, task quota and max in-flight. Push webhooks (`/api/public/foundry/webhook`) require an HMAC match on `FOUNDRY_WEBHOOK_SECRET` and charge the same budget. `/accounts` lists live connection state, scopes, credential location and revocation; it never stores tokens.
- Site log (`site-log.ts` tested rules, `site-log.server.ts`, `site-log.functions.ts`, `/site-log`): `site_log` is append-only (trigger rejects update/delete); every write goes through `logSite`, which redacts tokens/keys/JWTs/emails. Foundry `event()` mirrors into it. A DB trigger enqueues `log_outbox` rows per enabled `log_subscriptions` target; `deliverOutbox` (hourly tick + owner button) POSTs `jackboy.site-log/v1` with `Idempotency-Key` only when `<TARGET>_API_URL`/`_API_KEY` secrets exist, otherwise rows stay pending — never marked sent. JAX is off by default. Research uses GitHub's official search and returns references with SPDX license checks; patterns saved from research stay `verified_count 0` until a real tested repair uses them.
- AutoConnect (`autoconnect.ts` tested rules, `autoconnect.server.ts`, `autoconnect.functions.ts`, `/autoconnect`, hourly tick): per-project `capability_grants`; owner approval only moves a grant to `awaiting_setup` (`afterApproval`), and only a passing real API call (`afterVerify`) sets `connected`. Foundry marks tasks with `needs_capability` when tests can't run; a successful verification re-runs just that waiting step. Revoked/paused `github_repo` blocks Foundry inspections. Credentials stay in provider-issued backend secrets; Jackboy never mints or asks for keys in chat. All actions go to the site log (and thus the outbox).
- Updater architecture: repair authoring (Foundry) never ships packages; distribution is the signed release repository (`update-server*`) + enrolled targets (`update_targets`, hashed bearer tokens) + pure policy engine (`update-policy.ts`). Targets receive only the newest owner-published release that passes policy, report idempotent install phases to append-only `update_installs`, and failed health feeds auto-rollback and the Site Log. Reference client `scripts/updater-client.ts` verifies signature + SHA-256 and never executes payloads.
- Endpoint patching rules live in `endpoint-policy.ts` (pure, tested), separate from code repair and infrastructure updates; every patch needs signature, trusted provenance and owner approval, and device data may only come from enrolled clients.
- Patch catalog/triage/rings/exceptions/loop order live in `patch-catalog.ts` (pure, tested); the canonical concept→code status table is `docs/update-feature-matrix.md` — update it instead of adding dashboards, and keep vendor names out of product UI.
