## Jackboy feature rules (src/lib and their routes)
- Technology Discovery lives in `src/lib/discovery.ts` (source registry, dedupe, ranking, local state) and `src/routes/discovery.tsx`; it is opt-in and uses demo data until a backend can fetch public APIs/RSS on a schedule. Facts and AI hypotheses must stay visually separated.
- JAX is the commercialization/distribution hub. Release manifests (contract `jax.release-manifest/*`) live in `src/lib/jax.ts` + `src/routes/jax.tsx`; manifests stay `simulated: true` and `actualRevenue: null` until OMNI/JAX/payments are verified. Data-product revenue/distribution is gated by `dataProductCleared`; prohibited items (code, user data, credentials, PII, telemetry, third-party content, Vault) are never included.
- Discovery runs two tracks (`meta(f).track`): commercial (rankScore) and frontier/underdog (`frontierScore`, which must never take funding/publicity/citations/team size/sales as inputs). `mixTracks` reserves the owner-set frontier share (min 20%); `gemReasons` gives explainable overlooked-gem flags.
- Agent Hub (`src/lib/agent-hub.ts` rules, `agent-hub.functions.ts`, `/agents`, ingest at `/api/public/agent-ingest`): projects are opt-in; ingest uses project-scoped write-only tokens stored as SHA-256 hashes in `agent_project_tokens` (no client grants); DemonTech is limited to the defensive allowlist and owner-enabled per project; proposals are decided only via owner-only `decide_proposal` RPC and `tests_passed` stays false until a real sandbox runner exists.
- Automation policy (`src/lib/automation-policy.ts` rules, `automation.functions.ts`, `/automation`): single-row `automation_policy` changed only via owner-only `set_automation_policy` RPC (logged); `routeApproval` sends high-risk areas and production deploys to the owner at every tier; `guardian_verified` stays false until a real check exists; OMNI verification is read from `omni_connection`; retrieval uses owner-checked `playbooks` only, never private code or self-modification.
- Agent Fleet (`src/lib/guardian.ts`, `fleet.functions.ts`, `/fleet`): `agents` rows are per project; clients can update only name/specialty/autonomy/paused (column grants), so `installed_verified`/health are server-set. `guardianCheck` is deny-by-default (pause → verified install → project isolation → required integration → owner-only capabilities → autonomy tier); server `INTEGRATIONS` stay false until real checks exist. Emergency pause reuses `automation_policy.paused`.
- Agent Passport (`passport.functions.ts`, `/passport/$agentId`): Guardian denies any agent without `passport_approved`, set only by owner-only `approve_passport` RPC; a DB trigger voids approval when model/adapter/category/project/autonomy change. JAX enrollment is per agent via owner-only `set_jax_enrollment` (consent purpose required, Vault rejected). `omni_jobs` are inserted as `queued` with no `sent_at`; only `dispatchOmniJobs` may mark them sent. Ingest accepts optional `agent_id`, checked against project, category, passport and pause.
- RA'SUL integration (`src/lib/razul.ts` rules, `razul.functions.ts`, `/razul`): server-only via `RAZUL_API_URL`/`RAZUL_API_KEY` secrets; findings without a source URL, timestamp and evidence class are rejected (DB check too); routed OMNI jobs stay queued-unsent; feedback `sent_at` set only after a successful live POST.
- Update writer (`update-writer.ts` rules, `.server.ts`, `github.server.ts`, `feeds.ts`, `/projects` `/updates` `/feeds`, hourly cron + per-project frequency, webhook `/api/public/feeds/$sourceId` with hashed per-source token): owner-only RLS; DB lease + batch bound + monthly AI/run caps auto-pause; GitHub writes only to private repos via branch+PR, merge gated by `canMerge` (checks), revert restores stored previous contents; email alerts stay `not_configured` until a sender domain exists.
- Update server: pure rules in `update-server.ts` (tested), admin runtime in `update-server.server.ts`, owner fns in `releases.functions.ts`; public endpoints under `/api/public/updates/*` return only signed release/flag data keyed by a non-secret project `client_key`; signing key is derived from the `JACKBOY_SIGNING_SECRET` secret, so rotating it changes the public key.
- Autopilot (`autopilot.ts` tested rules, `autopilot.server.ts`, `autopilot.functions.ts`, `/autopilot`, hourly tick inside `/api/public/jobs/releases`): ships only when master AND project switches are on, checks are `success`, and no sensitive paths are touched (`canAutoShip`); otherwise fixes wait in the Update Queue. Auto-connect commits the shared `update-client-snippet.ts` via PR to private repos only. Site scans are static HTML (no JS). Chat (`chat.server.ts`, `/api/chat`, `/chat`) verifies owner bearer in the handler, uses tools over real data only, no chat history persistence.
- Demo findings (`detectDemo` in `autopilot.ts`) are review leads, not proof; "Remove Demo" always calls `writeFix(..., { forceApproval: true })` so it never auto-ships, and per-finding decisions live in `finding_decisions` keyed by `findingKey`.
- Chat voice is browser-only (`src/components/ChatVoice.tsx`: SpeechRecognition fills the editable input, speechSynthesis reads replies); no audio is recorded or stored, and controls hide when unsupported.
- Repo coding goes only through `repo-workspace.server.ts` (guards in `repo-workspace.ts`): private repos with push access, writes only on `jackboy/*` branches, protected paths refused, draft PRs only, never merge; chat must call `capabilities` before claiming build/test ability and never paste code instead of writing it.
- Code Foundry (`foundry.ts` tested state machine, `foundry.server.ts`, `foundry.functions.ts`, `/foundry`, tick inside `/api/public/jobs/releases`): tasks move only via `assertTransition`; every change appends to `foundry_events`, which a trigger makes immutable (no update/delete). Approval sets exactly one `approved_action` (draft PR or read checks) that runs once with an idempotency key and bounded attempts; connector failures → `blocked`, never fake success. Recurring inspections are off by default, rotate one project per run, dedupe by `(project_id, dedupe_key)` and respect a daily quota. Tokens stay in backend secrets, never in tables.
- Foundry pipeline: after a completed task `advance` reports the next awaiting task or runs one budgeted inspection of the next project; the hourly tick retries due transient-blocked tasks with exponential backoff (`backoffMs`) and honors global pause, daily run budget, task quota and max in-flight. Push webhooks (`/api/public/foundry/webhook`) require an HMAC match on `FOUNDRY_WEBHOOK_SECRET` and charge the same budget. `/accounts` lists live connection state, scopes, credential location and revocation; it never stores tokens.
- Site log (`site-log.ts` tested rules, `site-log.server.ts`, `site-log.functions.ts`, `/site-log`): `site_log` is append-only (trigger rejects update/delete); every write goes through `logSite`, which redacts tokens/keys/JWTs/emails. Foundry `event()` mirrors into it. A DB trigger enqueues `log_outbox` rows per enabled `log_subscriptions` target; `deliverOutbox` (hourly tick + owner button) POSTs `jackboy.site-log/v1` with `Idempotency-Key` only when `<TARGET>_API_URL`/`_API_KEY` secrets exist, otherwise rows stay pending — never marked sent. JAX is off by default. Research uses GitHub's official search and returns references with SPDX license checks; patterns saved from research stay `verified_count 0` until a real tested repair uses them.
- AutoConnect (`autoconnect.ts` tested rules, `autoconnect.server.ts`, `autoconnect.functions.ts`, `/autoconnect`, hourly tick): per-project `capability_grants`; owner approval only moves a grant to `awaiting_setup` (`afterApproval`), and only a passing real API call (`afterVerify`) sets `connected`. Foundry marks tasks with `needs_capability` when tests can't run; a successful verification re-runs just that waiting step. Revoked/paused `github_repo` blocks Foundry inspections. Credentials stay in provider-issued backend secrets; Jackboy never mints or asks for keys in chat. All actions go to the site log (and thus the outbox).
- Updater architecture: repair authoring (Foundry) never ships packages; distribution is the signed release repository (`update-server*`) + enrolled targets (`update_targets`, hashed bearer tokens) + pure policy engine (`update-policy.ts`). Targets receive only the newest owner-published release that passes policy, report idempotent install phases to append-only `update_installs`, and failed health feeds auto-rollback and the Site Log. Reference client `scripts/updater-client.ts` verifies signature + SHA-256 and never executes payloads.
- Endpoint patching rules live in `endpoint-policy.ts` (pure, tested), separate from code repair and infrastructure updates; every patch needs signature, trusted provenance and owner approval, and device data may only come from enrolled clients.
- Patch catalog/triage/rings/exceptions/loop order live in `patch-catalog.ts` (pure, tested); the canonical concept→code status table is `docs/update-feature-matrix.md` — update it instead of adding dashboards, and keep vendor names out of product UI.
- Projects page multi-select uses `batch.ts` (tested): per-project eligibility, skip with reason, bounded concurrency via `runBounded`, each project calls existing owner-checked per-project server functions; selection persists in sessionStorage keyed by user id. Device/endpoint patching is optional and kept out of the main workflow.
- Chat voice: browser SpeechRecognition, else MediaRecorder → owner-only `/api/transcribe` (gateway STT, audio never stored); voice-origin messages carry `metadata.voice` and `voice-guard.ts` blocks legacy change tools for voice; a generic spoken confirmation grants nothing. CODE uses a separate server-bound approval card.
- Shared agent contracts (VoiceGateway, GuardianPolicy, AuthorizationService, AgentRuntime) are types in `agent-contracts.ts`; Jackboy is the first implementation. Voice is intent, never identity: `voice-guard.ts#decideTool` refuses generic spoken confirmation. CODE approvals require the pending request ID, single-use nonce, expiry and authenticated session. Sensitive/production actions retain their existing passkey and provider-native paths.
- Shared agent manifest (`owner-agent.manifest/v1`, `agent-manifest.ts` tested; live checks in `agent-manifest.server.ts`; owner-auth `/api/agent/manifest`; chat `capabilities` tool): statuses come only from live checks; other projects adopt it later per project with separate authorization.
- Approval workflow buckets (pending / in progress / action required / history) come only from `src/lib/approval-state.ts`; approvals are conditional on the prior status (idempotent) and proposal notifications are unique per (kind, proposal).
- Passkey step-up (`step-up.ts` policy, `passkey.server.ts`, `passkey.functions.ts`, `step-up-client.ts`): permission is checked by role/action policy separately from the WebAuthn assertion; grants are single-use, action+target scoped, short-lived; merge/revert consume one. Quality metrics (`quality-metrics.ts`) report null, never 0%, without data.
- Code Foundry approvals go through `action_requests` cards (`action-approval.ts` rules; `requestAction`/`decideAction`): server-hashed single-use nonce re-issued per open, 15-min expiry, atomic pending→decided, Critical needs a passkey grant bound to the request id; outcome is read back from the task, never assumed.
- Code scan loop (`code-scan.ts` tested rules, `codeScan` in `foundry.server.ts`): bounded line-level source scan → AI fix → deterministic `validateFix` gates → commit on `jackboy/scan-*` → immutable checksummed `foundry_packages` manifest with rollback plan; only low-risk validated single-file fixes may auto-open a draft PR (actor `policy:routine-auto`); sensitive findings are blocked for owner review and never AI-fixed; merge/deploy always need owner approval.
- Background development (recurring Foundry inspections and push webhooks) runs only for `owner_projects.dev_enabled = true`, set per project by the owner via `setDevEnabled` (audited); order comes from `dev_priority` (`devPriority` in `connect-select.ts`). Inventory presence never implies authorization.

- GitHub access prefers a GitHub App (`github-app.ts` pure rules, `github-app.server.ts`, callback `/api/public/github/setup`): install links carry a signed 30-min owner state, the callback re-reads the installation with the app JWT, stores it in `github_installations`, then verifies and resumes waiting tasks; `githubTokenFor` uses short-lived installation tokens (auto-syncing installations from GitHub when none is recorded); the personal `GITHUB_TOKEN` is used only for repos in `PERSONAL_TOKEN_REPOS` and non-repo API calls. Chat's `authorizationHelp` tool is the only source of in-chat authorization links.


- CODE (`code.ts`, `code.server.ts`, `code-api.server.ts`, in-chat `CodeTasks.tsx`, official `.github/workflows/code.yml`): owner-only durable action_requests, separate Actions credential and explicit workflow-blob allowlist; no configured-only success claims, generic voice consent, automatic redispatch, agent credential sharing, merge or deployment. Read `docs/CODE.md` before changing it.
- OMNI link (`omni-link.ts` tested rules, `omni-link.server.ts`, `omni-link.functions.ts`, `OmniLinkPanel` on `/omni`, callback `/api/public/omni/callback`): `omni_connection.verified` is set only by a handshake in which OMNI returns HMAC(`OMNI_CALLBACK_SECRET`, challenge) with the `OMNI_API_KEY` bearer, and is re-proven every hour (a failure clears it). Queued `omni_jobs` are sent only while verified, with `Idempotency-Key` = job id and exponential backoff (max 8 tries). Callbacks need a fresh HMAC over `ts.nonce.body` plus a single-use nonce, and finished jobs never reopen. Approved CODE requests go to OMNI instead of the GitHub runner only when OMNI is verified. OMNI's side lives in `OMERTA-ROW/Omni` under `inbox/` and shares the HMAC test vector.
- GitHub App setup uses the Manifest flow (`github-app-manifest.ts` tested rules, `github-app-setup.functions.ts`, `/api/public/github/manifest` + `/webhook`, `GitHubAppPanel` on /settings): the running app cannot write Project Secrets, so created app credentials are stored AES-GCM-encrypted in service-only `github_app_credentials` (key `GITHUB_APP_ENCRYPTION_KEY`); env secrets override it. App installation tokens are preferred per repo; GITHUB_TOKEN is fallback only.
- Lovable deployment (`lovable-deployment*`, `/deployments`) reads only registered project references and uses the separate `LOVABLE_DEPLOY_API_KEY`, never the AI gateway `LOVABLE_API_KEY`; publishing is owner/passkey-gated and requires successful GitHub Actions for the exact provider-reported commit. Preview URLs are not commit-pinned. Lovable's documented API has no rollback endpoint, so rollback is a logged manual version-history handoff followed by the normal build and publish gates.
- Provider permission management (`provider-permissions*`, `/provider-access`) records each request, decision, and provider-observed permission change in append-only `provider_permission_events`; increases require owner/admin plus a request-scoped passkey, then the provider's official settings page. Jackboy never mutates GitHub App permissions itself.
- Physical building controls remain disabled: no provider credentials, device routes, or operation path may be added until ownership, supported provider authentication, and explicit authorization are independently verified. OMNI continues to use the existing authenticated/verified queue; deployment and permission actions are never automatically delegated.

- Reverse OMNI link (`omni-session*`, `/api/public/omni/link`, optional Node HTTPS adapter) is disabled by default and supports only `protocol.self-test`. Service-only sessions/jobs reuse owner/project/pause and immutable Site Log; never set `omni_connection.verified` from this reverse handshake or bypass CODE cards. No user code, shell, GitHub credentials, merge/deploy, or autonomous runner. See `docs/OMNI-SECURE-LINK.md` for the Cloudflare/Node boundary and approval gates.
- Hard limits live in code: a partial unique index allows one in-flight `foundry_tasks` row per project (`projectSlotFree` guard queues the rest), and `spikeGuard` pauses all Foundry work and notifies the owner when hourly inspections/AI attempts exceed `foundry_schedule.spike_limit_per_hour`; only owner "Resume all" clears it.
- GitHub credential order: live App installation first (`githubAvailable`/`githubTokenFor`), GITHUB_TOKEN only as optional fallback; the app must work with no token. Site detection order: repo homepage → GitHub deployment statuses → published *.lovable.app; dead-project archiving always needs owner confirmation and re-verifies before archiving.
- Project cards derive connection status only from `project_github_checks` evidence via `cardConnection` (src/lib/project-hub.ts); never show Connected without a verified read. Passkey recent-verification reuse is limited by `recentEligible` in `step-up.ts` and always mints a single-use grant tagged `recent:`.
- Account UX: `/auth` shows social buttons only when public Auth settings report the provider enabled (GitHub unsupported); password sign-in steps up to TOTP (aal2) when a verified factor exists; `/account` reads role via `my_role`, `/security` manages TOTP/password; self-signup never grants a role.
- Recovery (`recovery-codes.ts` rules, `recovery.functions.ts`, `/recover`, Security page): codes are salted SHA-256 hashes in `mfa_recovery_codes`, generated only from aal2 sessions, consumed by conditional update, 5 failures/15 min; redeeming removes TOTP factors and signs out other sessions but never touches roles or passkeys.
- Chat page: Chat and CODE are separate modes with per-account conversation history in browser storage (`chat-history.ts`, keyed by user id, titles redacted); the status pill uses only `deriveActivity` (`chat-status.ts`) over real voice/stream/CODE events; repo pickers and admin links live in side drawers, never the main canvas.
- Voice-first pattern (reusable for future agents): live voice and typed chat share one authenticated tool path (`buildJackboyTools` + `guardTools`); `app.delegation.pending` drives the Working status; mic/device failures map through `micErrorMessage`; the chat drawer shows device support, mic permission and privacy facts.
